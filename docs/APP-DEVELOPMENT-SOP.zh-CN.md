# CSV Import Preflight APP 开发与落地 SOP

> 版本：0.1  
> 目标：把现有 Landing Page 扩展为可以读取真实 CSV、完成本地预检与清洗、导出结果，并最终支持收费的产品。  
> 核心边界：CSV 数据默认只在用户浏览器中处理，不上传服务器。

## 1. 产品目标

目标用户：需要把联系人 CSV 导入 CRM 的运营人员、虚拟助理、销售运营和小型企业。

用户完成一次任务的标准流程：

```text
打开 /app
→ 选择 CSV
→ 确认字段
→ 设置检查规则
→ 运行 Preflight
→ 复核异常
→ 下载 clean / rejected / duplicates / report
```

第一版解决的问题：

- 导入前发现缺少必填字段；
- 检查 Email、电话和日期格式；
- 统一空格、Email 大小写和日期格式；
- 按 Email 或电话寻找完全重复的联系人；
- 分离可导入行和需要人工复核的行；
- 保留每一次修改和拒绝原因。

第一版不解决：

- 不直接连接 HubSpot、Salesforce 或其他 CRM；
- 不提供云端文件保存；
- 不进行 AI 模糊匹配；
- 不判断邮箱是否真实存在；
- 不处理 XLS/XLSX；
- 不做多人协作；
- 不做后台定时任务；
- 不接支付和 License。

## 2. MVP 默认规格

如果没有额外决定，开发按以下默认值进行：

| 项目 | 默认值 |
|---|---|
| 产品语言 | 英文 |
| 文件类型 | `.csv` |
| 编码 | UTF-8；检测 UTF-8 BOM |
| 文件上限 | 20 MB |
| 建议行数上限 | 50,000 行 |
| 数据处理位置 | 用户浏览器 |
| 日期输出 | `YYYY-MM-DD` |
| Email 处理 | 去除首尾空格并转小写 |
| 电话处理 | 去除无意义字符；用户选择默认国家/地区后再标准化 |
| 去重方法 | Email 或电话完全匹配 |
| 原始文件 | 不修改、不覆盖 |
| 导出文件 | `clean.csv`、`rejected.csv`、`duplicates.csv`、`preflight-report.csv` |
| 账号系统 | 无 |
| API | 无 |

## 4. 开发阶段 SOP

### Phase 0 — 冻结范围

工作：

1. 确认 MVP 默认规格；
2. 创建产品需求清单；
3. 创建虚构数据集；
4. 写出每条清洗规则的输入和预期输出；
5. 确认错误分类与导出格式。

完成标准：

- 每条规则都有测试例子；
- 不存在“自动修复所有错误”这类模糊要求；
- 明确哪些行可以自动修复，哪些必须人工复核；
- 所有测试数据均为虚构或已脱敏。

### Phase 1 — 建立 `/app` 操作界面

页面状态：

1. 空白状态：选择或拖放 CSV；
2. 文件预览：显示文件名、大小、行数、列名；
3. 字段映射：选择 Email、电话、日期和必填字段；
4. 规则设置：选择去重依据和日期输出格式；
5. 处理中：显示真实进度，不显示假进度；
6. 结果页：显示 Ready、Review、Duplicate 和 Rejected；
7. 导出页：分别下载四种结果。

完成标准：

- `/` Landing Page 保持正常；
- `/app` 可以在桌面和手机打开；
- 键盘可以操作主要控件；
- 错误提示说明问题及解决方法；
- 刷新页面不会把文件上传到任何服务器。

### Phase 2 — 建立 CSV 清洗引擎

建议模块：

```text
src/cleaner/
├─ parse.js
├─ map-columns.js
├─ normalize.js
├─ validate.js
├─ deduplicate.js
├─ summarize.js
└─ export.js
```

处理顺序：

```text
读取文件
→ 解析 CSV
→ 检查表头
→ 字段映射
→ 保留原始值
→ 标准化
→ 校验
→ 去重
→ 分类
→ 生成摘要
→ 导出
```

每个输出行至少保留：

- 原始行号；
- 当前状态；
- 错误代码；
- 错误说明；
- 修改字段；
- 修改前值；
- 修改后值。

完成标准：

- 相同输入和规则始终产生相同输出；
- 原始 CSV 永远不被覆盖；
- 自动修复和拒绝都有明确原因；
- CSV 中的逗号、换行、双引号和 Unicode 字符不会损坏；
- 处理失败时不生成看似成功的文件。

### Phase 3 — 自动测试与人工 QA

必须测试的数据集：

1. `duplicate-contacts.csv`：重复 Email、重复电话、大小写差异；
2. `mixed-formats.csv`：多种日期、电话、空格和 Email 格式；
3. `missing-required.csv`：缺少姓名、Email 或自定义必填字段；
4. `csv-edge-cases.csv`：逗号、双引号、换行、中文和 Emoji；
5. `large-sample.csv`：用于性能测试的大型虚构文件。

检查项目：

- [ ] 解析行数正确；
- [ ] 表头正确；
- [ ] UTF-8 字符没有乱码；
- [ ] 重复判断可解释；
- [ ] 导出后可以重新导入；
- [ ] 四种输出的行数可以互相核对；
- [ ] 桌面与手机没有横向溢出；
- [ ] 浏览器控制台无错误；
- [ ] 20 MB 上限有清晰提示；
- [ ] 页面关闭后不保留 CSV 内容。

完成标准：

- 所有自动测试通过；
- 三个主要测试文件人工核对通过；
- 没有数据丢失或错误归类的高严重度问题；
- Vercel Production 构建通过。

### Phase 4 — Private Beta

Beta 流程：

1. 邀请 3–5 位测试者；
2. 只使用虚构或已脱敏数据；
3. 让测试者独立完成一次完整流程；
4. 不在旁边逐步指导，观察哪些说明不够清楚；
5. 收集失败文件类型、错误信息和期望结果；
6. 修复阻断使用的问题；
7. 重新跑完整测试。

反馈问题：

- 你想导入哪个 CRM？
- 哪一步最难理解？
- 哪一种错误最有价值？
- 哪一种自动修改让你不放心？
- 导出的报告是否足以交接给同事？
- 你是否愿意为这个结果付款？为什么？

Beta 完成标准：

- 至少 3 人完成完整流程；
- 至少 2 人能在没有即时帮助下完成；
- 没有数据损坏问题；
- 已记录所有建议但只修复阻断销售的问题；
- 明确一个最常见的目标 CRM 或使用场景。

### Phase 5 — 付费与 License

推荐架构：

```text
付款平台
→ Webhook
→ Vercel API
→ 创建 License / entitlement
→ 用户登录或输入 License
→ /api/license/verify
→ 解锁 /app
```

重要边界：

- API 只验证付款和 License；
- CSV 继续在浏览器本地处理；
- Webhook 必须验证签名；
- 不把付款成功页面当作唯一付款证据；
- 不在前端代码中保存 API Secret；
- License 验证失败时不能删除或锁住用户的原始文件。

付费版完成标准：

- 测试付款可以正确创建 License；
- 退款或取消后权限行为明确；
- Webhook 重复发送不会创建重复记录；
- 无效 License 有清晰提示；
- Privacy、Terms、Refund 页面已发布；
- 客户知道怎样取得支持。

### Phase 6 — 正式发布

发布清单：

- [ ] GitHub `main` 分支为可发布版本；
- [ ] Vercel Production 构建通过；
- [ ] 自定义域名可选，不是首发阻挡；
- [ ] Landing Page CTA 指向真实 `/app`；
- [ ] 公开功能与软件实际功能一致；
- [ ] 截图和演示使用虚构数据；
- [ ] 价格、退款和 License 内容一致；
- [ ] 支持邮箱可以正常收信；
- [ ] 准备版本号和变更记录；
- [ ] 准备回滚到上一个稳定版本的方法。

## 5. 上线后的运营 SOP

### 每次发布

```text
建立修改
→ 本地测试
→ Production build
→ Git commit
→ Push GitHub
→ Vercel Preview / Production
→ 浏览器验收
→ 记录版本变化
```

### 收到 Bug

要求用户提供：

- 浏览器名称和版本；
- 文件大小、行数和列数；
- 错误截图或错误文字；
- 可以复现问题的最小虚构 CSV；
- 用户选择的规则；
- 预期输出。

不要要求用户发送完整客户 CSV。若必须检查文件，应先让用户删除或替换个人资料。

### 问题优先级

| 等级 | 定义 | 处理原则 |
|---|---|---|
| P0 | 数据损坏、错误导出、隐私泄露 | 停止发布并优先修复 |
| P1 | 无法上传、处理或下载 | 尽快修复 |
| P2 | 某种格式或规则不正确 | 排入近期版本 |
| P3 | 视觉、文案或新功能建议 | 进入待办，不阻挡销售 |

## 6. 双方职责

### 产品拥有者负责

- 决定产品名称、目标客户和收费模式；
- 提供或批准虚构测试场景；
- 安排 Beta 测试者；
- 处理 SSM、税务、收款和法律政策确认；
- 决定是否收集分析数据；
- 决定最终定价、退款和支持承诺。

### Codex 开发负责

- 设计并实现 `/app`；
- 建立本地 CSV 处理引擎；
- 创建虚构测试数据；
- 编写自动测试；
- 进行桌面和移动端 QA；
- 维护 GitHub 和 Vercel 部署；
- 编写用户说明和技术交付文档；
- 清楚报告未知限制和未完成项目。

## 7. Definition of Done

只有以下条件全部满足，MVP 才算完成：

- 用户可以使用真实 CSV 完成上传、配置、检查和导出；
- CSV 不上传服务器；
- 原始文件不被覆盖；
- 每个错误和修改都可解释；
- 四种输出文件可正常打开；
- 自动测试和人工 QA 通过；
- 桌面和手机版可用；
- Landing Page 不再展示未实现的功能；
- GitHub、Vercel 和 README 同步；
- Beta 用户有明确的反馈入口。

只有完成 Beta、商业注册、收款、License 和政策页面后，才进入正式付费销售状态。
